## Experiments

### November 9: first worker run on T-001, environment failure

**Question:** does one labeled issue produce one draft PR?

**Configuration:** `worker.yml` at `60ac97e`, `claude-code-action` v1.0.269,
`claude-sonnet-5-5`, `--max-turns 60`, `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1`.
[Run 42662156686](https://github.com/rhprasad0/factory-scoreboard/actions/runs/42662156686),
transcript saved as a workflow artifact.

**Result:** no. The job was green, but there was no branch, commit or PR.

| Measure | Value |
| --- | --- |
| Turns | 8 |
| Job wall-clock | 58 seconds |
| Claude duration | 16 seconds |
| Reported cost (notional under Max) | $0.0766 |
| Shell commands that ran | 0 |
| Graders run | None |

**Cause:** every Bash call failed with "Sandbox dependencies not available: socat not
installed". We set the scrub directly, and the action only installs `bubblewrap` and
`socat` when `allowed_non_write_users` is set.

**Fair?** No. This was a broken environment, not a worker error, so it is excluded from
pass@1 and no eval record was written. The worker reported accurately that it had written
files but could not build, commit or open a PR.

**Second finding:** the action reports success whenever Claude finishes normally, so the
run was green with nothing to show. The human watching it read that as success.

**Retained:** the scrub stays on. `worker.yml` now installs the sandbox dependencies and
fails the job if no PR exists for the issue.

**Limits:** the fix has not run yet. Whether `cargo` can reach crates.io from inside the
sandbox is unknown until the next run.

### November 9: second worker run on T-001, graded November 10

**Question:** with the sandbox installed, does one labeled issue produce a PR that passes
the hidden oracle?

**Configuration:** `worker.yml` at `dc33804`, otherwise the same as the first run.
[Run 42663612461](https://github.com/rhprasad0/factory-scoreboard/actions/runs/42663612461),
[PR #7](https://github.com/rhprasad0/factory-scoreboard/pull/7) at `a4814be`, transcript
saved as a workflow artifact. This is the second run but trial 1, because the first run
was excluded.

**Result:** yes. The worker opened a draft PR from `claude/issue-4` with `Closes #4`, and
every grader that ran passed.

| Measure | Value |
| --- | --- |
| Turns | 24 |
| Job wall-clock | 136 seconds |
| Claude duration | 90.7 seconds |
| Reported cost (notional under Max) | $0.1539 |
| Tool calls blocked by the permission checker | 8 of 23 |
| Changed lines | 1,275, of which `Cargo.lock` is 1,202 |

| Grader | Verdict | Evidence |
| --- | --- | --- |
| build | pass | `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test` run locally at `a4814be`, and green in CI |
| pass-to-pass | pass (vacuous) | The base commit has no `app/`, so no visible tests existed to keep passing |
| oracle | pass | `tasks/4/` from the holdout repo at `b804982`, 1 passed, run by hand |
| hygiene | pass | `hygiene.py` run locally and in CI, no signals |
| scope | not run | The judge arrives in weeks 3-4 |
| human | not run | The PR has not been reviewed yet |

The critical classifier flagged the PR with `dependency` and `oversized`. Only
`dependency` means anything here, since the lockfile alone makes the PR oversized and any
PR that changes it is already critical.

**Cold build:** it fit easily. The cache lookup found nothing, and the whole job took 136
seconds against a 30-minute timeout. CI's cold build took 51 seconds. That also answers
the first entry's open limit: `cargo` reached crates.io from inside the sandbox.

**Fair?** Yes. The issue body hashes to the `spec_sha` in `tasks/4/task.json` once the
trailing newline added by `gh --jq` is removed, and the PR's merge base matches
`base_commit`. None of the worker's 23 logged tool calls mention the holdout repo. The
graded tree stayed clean through the build, so what passed is exactly `a4814be`.

**Second finding:** Claude Code's permission checker, not the bubblewrap sandbox, blocked
8 of the worker's 23 tool calls: 7 reported as permission denials and one `sleep` chain
refused by the tool. Three were setup or check commands the worker got past with Write or
a simpler command. The other five were attempts to check `/health` live, and none got
through, because `curl` is not allowlisted and the checker refuses loops and variables it
cannot read in advance. All three required cargo checks still completed, and the evidence
comment said the live check had not. Only the oracle proved the route on port 9000.

**Retained:** the sandbox and the "Require a PR" step.

**Limits:** one trial, one oracle test, so this says nothing about pass^3. The hand-run
oracle started from a warm build, so it did not test a cold start under `cargo lambda
watch`. The holdout check covers tool calls in the transcript and is otherwise the honor
system.

**Next:** `factory/friction.py` now reports blocked calls per trial from the transcript.
Trials need that data before any allowlist change can be compared against this baseline.
